1

背景

BioChat 目前只会用文字回答生物多样性问题——统计类问题（数量、排名、均值）从 Solr 拼真实数字，描述类问题 （“What are silverfish?”）走 OpenSearch 检索 + LLM 生成带引用的说明。不管问的是什么，聊天框里出来的 永远只是一段话，用户想再看具体标本记录，得自己手动去 Search 页面重新筛选一遍。

这份文档记录的是：如何让聊天机器人在识别出“用户想看具体记录”时，直接带着筛选条件把用户带到 Search 页面。

2

目标

与 Angel Chang 确认过的两个具体场景：

“How many Phoridae specimens in Costa Rica?” — 这类问法不必自动执行跳转，可以先给答案，附带一个后续 选项。

“Show me the Phoridae specimens in Costa Rica” — 这类问法应该直接跳转到 Search 页面，自动应用 family: Phoridae、country: Costa Rica 两个筛选条件，展示真实匹配的记录。

—— Angel Chang，聊天记录，2026-08

关键在于：两句话问的信息完全一样（同一批标本），但表达方式不同，期望的产出形态也不同。这不是简单的 “加一个新问题类型”，而是要在现有系统上再加一根判断轴。

3

现状与缺口

分类 LLM（hybrid_query_router.py）目前把每个问题归到 6 类之一，全部只产出文字：

query_type典型问法数据来源是否过生成式 LLM
countHow many Phoridae in Costa Rica?Solr否，模板拼字符串
listList all families in CanadaSolr facet否
topWhich country has the most Phoridae?Solr facet否
aggregateAverage elevation for Diptera?Solr stats否
distributionSpecimen counts by countrySolr facet否
descriptionWhat are silverfish?OpenSearch 检索是，带引用生成

缺口很直接：这 6 类里没有一类是“把实际标本记录带到 Search 页展示”。“Show me the Phoridae specimens in Costa Rica”这种问法目前会被硬塞进 list 或 count，只能吐一句文字，触发不了跳转。

4

核心设计：两根正交轴

最初的思路是“新增第 7 个 query_type”，但站不住——“统计类”和“描述类”问题本身也可能带指令语气（“Show me how many…”仍然只是要个数字）。真正要判断的是两件独立的事，需要拆成两根轴，分别由分类 LLM 一次性输出：

内容轴 query_type

用户想要哪种内容——决定去哪查数据、答案文字怎么来。不变，仍是原来 6 选 1。

  • count / list / top / aggregate / distribution
  • description

动作轴 display_intent

这段回答之外，要不要顺带触发一次跳转——新增，3 选 1。

  • none — 无可跳转的筛选条件
  • suggest — 附带可选的“查看记录”按钮
  • auto_navigate — 直接跳转

两轴互不影响：query_type 决定聊天框里那句话怎么生成，display_intent 决定要不要在 那句话旁边附加一个跳转动作。filters（family/country 等实体）本身是 所有 6 类内容都会抽取的通用产物，动作轴只是把它多利用了一次。

5

模块职责

模块职责状态
Clients 聊天面板发问句、展示回答；命中 action 时渲染按钮或直接调用 navigate() 跳转 Search 页 已有
Interface /v2/chat 网关，协调各服务，把 answer_text 与 action 合并成一个响应 已有，需扩展响应字段
Query Parsing Service 分类 LLM，一次性输出 query_type + filters + display_intent 已有，需新增 display_intent 维度
Answer Generation Service 按 query_type 生成正文文字——统计类查 Solr 套模板，描述类查 OpenSearch 后走生成 LLM 已有，逻辑不变
Interaction Service 仅在描述类内部被调用：识别捕食/寄生/传粉等生态学问题，把 GloBI 文档优先排到检索结果前面 已有，原样复用
Instruction Route Service 依据 display_intent 决定要不要查库校验 filters、要不要组装跳转 action 新增
DB Solr（标本元数据，统计类 + 校验共用）、OpenSearch（知识库检索，描述类专用） 已有

6

端到端流程

一条问句进来后分成两条并行支路：左上是原有的“答案怎么来”，左下是新增的“要不要跳转”。两条支路都可能 用到 DB，最后在 Interface 汇合成一个响应。

逐步说明

  1. Client 发送原始问句到 Interface（/v2/chat）。
  2. Interface 转发给 Query Parsing Service，LLM 一次性输出 query_type / filters / display_intent。
  3. Answer Generation Service 按 query_type 生成正文：统计类查 Solr 套模板，描述类查 OpenSearch 后过生成 LLM。
  4. 若 display_intent ≠ none，Instruction Route Service 用 filters 去 Solr 校验是否有匹配记录；统计类可直接复用 Answer Generation 那次查询已拿到的 numFound，描述类需要单独查一次。
  5. 有匹配 → 组装 action（suggest 附按钮，auto_navigate 直接跳转）；无匹配 → action 为 null。
  6. Interface 合并 answer_text 与 action，一次性返回给 Client。

7

响应结构

Query Parsing Service 的分类输出（内部）：

{
  "query_type": "count",
  "filters": { "family": "Phoridae", "country": "Costa Rica" },
  "display_intent": "suggest"
}

/v2/chat 返回给前端的最终响应——在现有 OpenAI 兼容字段基础上，新增 bioscan_action：

{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": "Found 42 Phoridae specimens in Costa Rica."
    }
  }],
  "bioscan_action": {
    "type": "auto_navigate",        // suggest | auto_navigate
    "filters": { "family": "Phoridae", "country": "Costa Rica" },
    "result_count": 42
  }
}

bioscan_action 为 null 时前端只渲染 content；type 为 suggest 时渲染一个“查看记录”按钮，点击后才拼 URL 跳转；为 auto_navigate 时前端 直接用 filters 拼 Search 页 URL query string 并调用 navigate()。字段名 （family / country / order / genus / species） 与 Search 页 FILTER_TYPES 已完全对齐，不需要额外映射。

8

边界情况

  • filters 校验为 0 条匹配——例如 LLM 抽取的国名拼写有误。action 置为 null，正文补一句“未找到匹配记录”，不跳转。
  • 描述类 + 明确指令同时出现——如“Tell me about Phoridae, show me some in Costa Rica”。 query_type=description 正常走 RAG 生成说明文字，display_intent=auto_navigate 触发单独一次 Solr 校验查询（因为 description 路径本身不碰 Solr）。
  • 没有可用 filters 的展示型问法——如“show me some interesting specimens”，没有具体 taxon/country 可抽取。display_intent 应退回 none，不强行跳转到无筛选的 Search 页。

9

待确认的开放问题

  1. display_intent 的判定边界
    哪些措辞算“明确要求查看”（auto_navigate）、哪些只算“可以顺带提供入口”（suggest）？需要在分类 prompt 里写清楚区分规则，并用真实问法样本跑一轮准确率评估。
  2. 0 匹配时的兜底文案
    是直接说“未找到”，还是尝试放宽某个筛选条件再问用户一次（比如去掉 country 只按 family 查）？
  3. suggest 按钮的交互归属
    用户点击“查看记录”按钮后的跳转逻辑放在 Clients 内部处理即可，还是也要经过 Interface 记一次日志？

10

验收标准

  • “Show me the Phoridae specimens in Costa Rica” 类问法能直接跳转到 Search 页，且 family、country 筛选条件已自动应用
  • “How many Phoridae specimens in Costa Rica?” 类问法只返回文字答案，附带 一个可选的“查看记录”入口，不自动跳转
  • count/list/top/aggregate/distribution/description 六类问法的现有行为 不受影响，回归测试全部通过
  • filters 在 Solr 中查无匹配时，不触发跳转，聊天框给出明确提示
  • /v2/chat 响应新增的 bioscan_action 字段不破坏 现有 OpenAI 兼容客户端
